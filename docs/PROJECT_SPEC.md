# 产品需求文档（PRD）— ServiceFlow

## 1. 业务背景与问题

电商售后通常要跨多个数据源完成订单查询、业务政策核查、取消/修改、退换货和人工交接。纯RAG客服只能回答问题，无法安全完成写业务操作；纯单Agent容易面临工具权限过宽、上下文拥挤、错误调用不易定位等问题。项目旨在用可分工、可控、可测的智能执行链路替代演示型聊天机器人。

项目**不是**真实电商支付平台。τ-bench Retail为模拟业务数据；所有“业务执行”初期只修改本地模拟数据库。

## 2. 目标角色

1. 消费者：咨询自己的订单、查询规则、提出取消/修改/退换货请求、明确确认。
2. 售后人员：查看工单、核验困难场景、接管对话、批准或拒绝特殊申请。
3. 开发者：查看 Agent 执行轨迹、失败诊断与评测对照。

## 3. 明确的 MVP 范围

**Must Have（首版）**：
- 通过模拟身份验证关联唯一用户；按用户归属校验所有订单访问。
- 查询用户资料（仅授权字段）、本人订单、商品及可用变体。
- 订单取消（pending）、订单修改（符合政策时）、已送达商品退货/换货（按实际工具能力逐项支持）。
- 提示操作详情 → 用户确认 → 重新读取状态 → 硬规则验证 → 执行 → 写审计 → 明确反馈。
- 多 Agent编排、最小可验证的政策检索、失败转人工。
- 单 Agent 基线、任务评测、关键安全边界测试。

**Should Have（第二阶段）**：
- 工单后台、人工审批、会话断点续接、失败恢复、文档RAG、可视化轨迹。

**Won't Have（首版不做）**：
- 真实资金转账/外部退款支付、微信等多渠道、语音、复杂CRM、全量微调、未接入系统的自动发货。

## 4. 关键用户故事（示例）

**US-01：订单查询**
- 我作为消费者，通过模拟验证后问“我最近的订单到哪一步了”；系统仅返回我的订单状态及可访问物流信息。
- 验收：越权订单查询被拒；回答字段全部可追溯到数据库。

**US-02：取消订单**
- 我作为消费者，对 pending 订单提出取消；系统说明订单号、影响范围和后果，等待我明确确认，再执行。
- 验收：订单状态不符/无确认/重复确认均不能造成错误写入。

**US-03：退货**
- 我作为消费者，对 delivered 订单的部分商品申请退货，系统检查政策、商品范围和退款途径，说明方案并等待确认。
- 验收：操作项精确匹配用户确认内容；执行失败不谎称成功。

**US-04：复合请求**
- 我询问物流并要求取消另一笔订单；系统先核验身份，再读取两笔订单，按政策分别处理。
- 验收：不同订单不会串单；用户追加要求后更新操作提案。

**US-05：人工接管**
- 业务范围之外的情况，自动创建工单并交人工处理。
- 验收：转交后Agent不能继续执行未获授权的高风险操作。

## 5. 业务流程（文字版）

用户输入 → 会话身份检查 → Triage理解诉求 → Order读取数据 / Policy读取政策 → Resolution制定方案 → 硬规则校验 → 若为只读则回答；若为写操作则生成操作提案（proposal）→ 用户明确确认 → 执行前重新验证身份和数据库状态 → 幂等执行 → 审计 → 回复；若不能处理则转人工。

## 6. 功能验收

- 主业务能力必须有真 API/工具实现和对应数据库变更，不接受只在聊天中宣称“已处理”。
- 100%关键写路径需要身份校验、明确确认、服务端规则和审计；不能用模型自行判断取代。
- 在异常场景中无意外数据泄露、无重复写入（测试预期，不代表已达到）。
- 业务流程每一步可由 trace_id / ticket_id / operation_id 追溯。

## 7. 非功能需求

- 开发环境一键安装/初始化数据库；导入脚本幂等且可复位。
- 含API错误码、日志追踪、超时/重试边界、最小权限。
- Prompt注入、查询越权、重复请求、政策冲突等都必须通过代码级测试。
- 多Agent相对单Agent若无优势，应客观报告，不为架构辩护而修改数据。
