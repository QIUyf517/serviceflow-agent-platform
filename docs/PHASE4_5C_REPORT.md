# 阶段 4.5C：中文体验与人工接管

日期：2026-11-14

## 实现

顾客端把查询、操作提案、拒绝、失败、执行结果和工单状态展示为中文；开发者页保留技术标识。恢复历史任务时，旧版英文终端提示以中文恢复说明替代。取消与退货的服务端成功答复从实际执行结果生成；退货明确说明本地申请不等于真实退款。

只有客户明确请求人工才建立工单。商家后台每 5 秒检查新工单，查看脱敏会话和经工单客户归属验证的订单状态及商品项数量。操作员回复通过事务写入 `messages` 和 `audit_events`；客户通过已核验、绑定同一会话的接口读取回复和状态。人工回复不会生成订单操作，也不会代替客户确认。

顾客端从同一已核验会话恢复最近 200 条对话消息，刷新页面后仍能继续追问。取消原因追问承接“不要了”“不再需要了”及常见错字“不在需要了”；收到原因后只生成待确认提案，不自动写订单。

## API

- `POST /api/v1/tickets/{ticket_id}/reply`：操作员 token、`{"content":"人工客服正在核对这笔订单。"}`；返回消息序号、内容和时间。终态工单拒绝回复。
- `GET /api/v1/customer/tickets`：只返回当前已核验会话的工单编号、状态、关联订单号和时间。
- `GET /api/v1/customer/tickets/{ticket_id}/updates`：只返回该会话、该客户的工单状态及人工消息；跨会话返回 404，未核验返回 403。
- `GET /api/v1/customer/conversation`：输入 `X-Session-Id: <已核验的本顾客会话>`；输出最近 200 条 `[{"sequence":1,"role":"user","content":"取消这个订单","created_at":1730000000}]`，未核验返回 403。

## 边界

这是本地模拟商城和操作员 token，不是生产 IAM 或实时推送；页面每 5 秒轮询一次。旧历史消息不会迁移或重写，开发者轨迹仍可见上游英文技术标识。阶段 4.5 收尾验收尚未进行。

## 2026-11-15 双向人工会话修订

人工验收发现原实现只自动同步“操作员 → 顾客”：顾客收到人工回复后继续输入，消息仍走 `/api/v1/multi-agent/chat`；后台只轮询工单列表，不轮询已打开的工单详情。因此消息虽然进入会话表，但没有绑定工单、不会更新工单状态，操作员也无法及时看到。这是原 4.5C 验收覆盖不足，不应解释为使用方式问题。

修订新增 `POST /api/v1/customer/tickets/{ticket_id}/messages`。服务端要求已核验的 `X-Session-Id` 和 16–128 字符的 `Idempotency-Key`，校验 session、user 与 ticket 三者绑定；同一键同一内容复用原序号，同一键修改内容返回冲突，跨顾客访问返回 404。消息以 `role=user` 和具体 `ticket_id` 写入 `messages`，工单更新时间同步更新；`waiting_customer` 或 `resolved` 自动恢复为 `in_progress`。审计只记录序号和状态变化，不保存顾客消息正文。

顾客前端检测到非 `closed`/`cancelled` 的活动人工工单后，把普通输入发送到上述接口，不再调用 Agent；仍绑定执行请求的“确认/拒绝”继续走受控确认链，避免破坏客户确认语义。管理后台对当前工单详情和审计每 5 秒轮询，并允许后台标签页继续刷新。

修订后验收结果：

- 后端完整 pytest：**226 passed**。
- 前端 Vitest：**8 files、40 passed**。
- 真实 Chromium + FastAPI + PostgreSQL：**10 passed**；双标签页验证人工回复到达顾客、顾客继续回复、已打开后台自动显示。
- Ruff、ESLint、TypeScript、生产构建：通过。
- E2E 随机 PostgreSQL schema：残留 **0**。

首次浏览器重跑因 Playwright 更新后缺少对应 Chromium 而未执行到业务断言；安装匹配浏览器后原命令重跑 10/10 通过。另一次后端 PostgreSQL 补跑错误使用容器内主机名 `db`，改为宿主机 `127.0.0.1` 后相同四项验收 4/4 通过。这些环境失败未计入成功结果。

## 2026-11-15 刷新后人工工单恢复修订

继续人工复核时，顾客在页面刷新后回复“好的，请继续处理”显示 `http_500`。日志与数据库核对确认有两个独立缺陷：订单对话中通过自然语言“转人工”创建的工单未绑定 `order_id`，导致前端按当前订单筛选时找不到它，错误地把消息发送至 `/api/v1/multi-agent/chat`；该会话的旧 LangGraph 检查点又缺少后来增加的 `triage_result` 通道，于是旧接口抛出 `KeyError`。这不是顾客输入或操作方式错误。

修复包含三层：显式转人工时从已限定的订单消息中提取订单号，并由 `TicketService.create` 再次执行订单归属校验后绑定；前端优先选择当前订单的活动工单，若不存在则兼容恢复同一已核验会话中的旧未绑定活动工单；恢复旧检查点时以当前完整状态模型补齐所有非累加通道，并为累加通道提供空增量，避免新节点读到不完整状态。

新增后端用例断言订单范围内转人工得到绑定订单的工单；新增前端用例从已保存 session 启动、返回 `order_id=null` 的旧活动工单，并断言顾客回复进入工单消息接口且 Agent 调用次数为 0。真实 PostgreSQL 后端全套 **227 passed**，前端 **8 files、41 passed**；Ruff、ESLint、TypeScript 与生产构建通过。重新构建后的 db、api、frontend 均为 healthy。阶段 4.5 收尾的人工作业仍需在新版页面复核。

## 2026-11-15 人工客服聊天窗口修订

人工复核指出后台会话记录与回复表单相距过远，客服需要在同一案件卷宗内反复滚动。数据链路虽然可用，但不适合连续对话。此次只调整前端信息架构，不修改工单权限、API 或订单写操作边界。

后台现在把脱敏会话、同步状态和人工回复合并为一个固定高度的聊天窗口：顾客消息位于左侧，人工客服位于右侧，智能客服历史使用居中的中性样式；角色和时间戳继续保留。详情每 5 秒轮询后，窗口自动定位最新消息。输入框紧邻消息区，支持 Enter 发送和 Shift+Enter 换行；终态工单禁用回复。分配客服、合法状态流转、内部审批和人工代执行位于独立的“工单治理”区，避免把聊天回复误解为客户对订单写操作的确认。

新增前端测试验证会话与回复框处于同一个可访问区域，发送请求后人工消息在该窗口出现。最终前端完整测试 **8 files、42 passed**，ESLint、TypeScript 和生产构建通过；使用实际 Compose 后台工单完成桌面截图检查，未发现溢出或表单分离，frontend 容器 healthy。
