# 阶段 5B：V3 单订单会话边界固化与冻结报告

日期：2026-11-20（Asia/Shanghai）

## 结论

V3 已按产品范围重新冻结，并在 20 元人民币总预算授权下完成 holdout。最终 V3 为 45/120（37.50%），单 Agent 为 51/120（42.50%）；V3 未证明优于单 Agent。冻结后禁止使用该 holdout 调参或同版本重跑。

产品采用服务端拥有的单订单线程：一个 `support_thread` 最多绑定一笔订单。订单线程提到另一笔订单时返回 `order_scope_mismatch`；通用咨询线程提出取消、退货、换货或修改请求时返回 `order_thread_required`。两种情况均不会创建执行请求或修改订单，并在持久化消息元数据中记录路由结果。用户需要从“我的订单”进入目标订单的独立客服窗口。

这项冻结不代表支持一个窗口批量处理多笔订单。同一订单内多个商品仍可绑定到一份具体提案，经一次明确确认后在一个数据库事务中执行。

## 已核实的既有能力与补充改动

阶段 4.5D 已经实现 `support_threads`、订单归属核验、消息/工单/检查点隔离，以及订单线程中的跨订单拒绝。本轮没有重复建立线程模型，而是补齐两个缺口：

1. 通用咨询线程不再允许创建订单写操作，必须进入目标订单窗口。
2. 混合请求同时提到当前订单和另一订单时，零部分执行；如当前线程存在未执行提案，该提案被标记为 `superseded`，防止后续误确认。

新增回归还验证：同一订单的两件商品可形成一个退货请求、一个确认记录和一次 `execution_succeeded`，最终在同一事务中写入两个商品数量。

## API 输入输出示例

通用咨询线程收到订单写请求时安全停止：

```http
POST /api/v1/multi-agent/chat
X-Session-Id: <verified-session>
Content-Type: application/json

{"message":"帮我取消订单 #W1006327，因为误下单"}
```

```json
{
  "task_status": "order_thread_required",
  "pending_confirmation": null,
  "execution_result": null,
  "tool_results": [],
  "thread_kind": "general",
  "final_response": "通用咨询不能修改订单。请在“我的订单”中打开需要处理的订单客服窗口，每个窗口只处理其绑定订单。"
}
```

从订单入口提交相同请求时，输入必须包含服务端重新核验的 `order_id`；响应可进入 `pending_confirmation`，但在客户明确确认前不会写订单：

```http
POST /api/v1/multi-agent/chat
X-Session-Id: <verified-session>
Content-Type: application/json

{"message":"帮我取消订单，因为误下单","order_id":"#W1006327"}
```

第一次加入通用线程写保护后的完整回归有 5 项旧 API 测试失败，因为它们仍在通用线程发送写请求；测试已改为携带 `order_id` 进入订单线程。另一次完整运行中，一个与本轮无关的固定中文口语分类参数单次失败；隔离重跑 3/3 通过，随后完整套件 253/253 通过。该过程保留在报告中，不将中间失败伪装为首次通过。
